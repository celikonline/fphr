# 11.3.1 Kimlik ve Erişim

## Plan Kararları

**[Video] Erişim türleri, birim yetkilendirme, erişim ayarları ve davet** (ayrıntı Bölüm 11.3.1):
- **FARKLI — Erişim türü çalışan kartında tek alan** [Ekranda]: Kolay İK'da kullanıcı tipi **Çalışan / Hesap sahibi / Yönetici** olarak çalışan kartı içinde seçilir. Eşleme: Çalışan = `Employee`, Hesap sahibi = `Owner`, Yönetici = `Admin`; kalan 14 sistem rolü SenseİK genişletmesidir (Kullanıcılar > Roller). Karta **Erişim türü** hızlı seçici (`PUT /identity/users/{id}/access-type`); Owner'ı yalnız Owner atar/düşürür; son Owner düşürülemez; birden fazla Owner olabilir ("hesap sahipleri" çoğul).
- **FARKLI — Rol görünen adları** [Ekranda]: Kolay İK'da "Yönetici" = tam yetkili yönetici, "Birim yöneticisi" = birim yetkilisi; İngilizce UI'da Owner/Manager (part1). Plan tablosundaki `Manager` = "Yönetici" adı çakışır → kaynak anahtarları: `role.owner` "Hesap Sahibi", `role.admin` "Yönetici", `role.manager` "Birim Yöneticisi" (Team + birim kapsamı).
- **DETAY — Hesap sahibi vs Yönetici farkı yalnız Ayarlar > Ödeme bilgileri** [Ekranda, çelişkili]: transkript "ödeme bilgilerine hesap sahipleri ulaşamıyor, sadece yöneticiler" diyor; plan Owner = faturalama. **Doğrulanmalı**; karar: plan yönü korunur (`billing.*` Owner), rol matrisinden Admin'e verilebilir. Diğer tüm ayarlar, uygulamalar ve veri aktarımı iki tipe de açık.
- **YENİ — Birim yetkilendirme `UnitAuthorization{OrgUnitId, UserId, CanViewSalaryAndPayments, CanViewUnitReports, GrantedByUserId, IsActive}`** [Ekranda]: birim ağacında satır üç nokta → **Birim yetkilendirme** → kişi seç → iki anahtar → Kaydet. Unique `(TenantId, OrgUnitId, UserId)`; aynı kişi birden fazla birime. Identity sahibidir; Organization birim ağacı ekranı `POST /identity/unit-authorizations` çağırır; `OrgUnitId` yalnız Id referansı, doğrulama `IOrgUnitReadService` portu.
- **YENİ — Birim yetkisi üçüncü kapsam kaynağı**: etkin izin = roller ∪ `UserPermissionOverride` ∪ `UnitManagerGrants` (seed sabiti); kapsam `Department` (OrgUnit + alt birimler). `IDataScopeService.GetVisibleEmployeeIdsAsync` = rol kapsamı ∪ hiyerarşi (`IsManagerOf`) ∪ yetkili birimler. `UnitAuthorizationChanged` event'i permission `pv` sürümünü artırır.
- **DETAY — Birim yöneticisi izin seti** [Ekranda]: temel `employee.card.read`, `employee.personal.update`, `employee.career.update`, `employee.card.create`, `leave.request.read`, `leave.balance.read` @birim; anahtar 1 → `employee.salary.view` + `payment.record.read` @birim (Finans raporundaki maaş kolonları da buna bağlı); anahtar 2 → `reporting.report.run` @birim (hazır raporlar, birim filtresi zorunlu); `reporting.custom.build` (**Kendin oluştur**) hiçbir zaman verilmez.
- **DETAY — Birim yöneticisi kendi birimine çalışan ekler** [Ekranda]: **Yeni çalışan ekle**'de şirket/şube kendi kariyerinden ön-dolu gelir (düzenlenebilir); birim yetkili olduğu birimlerle sınırlı; yönetici, çalışma şekli, kişisel bilgiler girilir → `CreateEmployee` komutunda birim kapsam doğrulaması.
- **YENİ — Erişim ayarları (`TenantSettings` `access.*` grubu, 11 anahtar)** [Ekranda]: Ayarlar → Sistem ayarları → **Erişim ayarları**, tek **Kaydet**. Ana sayfa: `access.home.showUnitInfo` (adı okunamadı), `.showUpcomingLeaves`, `.showUpcomingBirthdays`, `.showEventCalendar`; Hesap: `access.account.showOwnFiles`, `.showOwnAssets`, `.showPhoneNumbers`, `.showOrgChart`, `.showCustomFields` (varsayılan kapalı; **birim yöneticileri** için); Takvim: `access.calendar.showMenu`, `.showAllLeaves`. `GET/PUT /identity/settings/access` (`identity.settings.access.manage`).
- **DETAY — Erişim ayarı yalnız Çalışan tipini (ve Özel alanlar için birim yöneticisini) kısıtlar**: Owner/Admin/HR etkilenmez. Sunucu tarafı `[RequiresAccessSetting(key)]` filtresi ilgili tam izni olmayan kullanıcıya uygulanır; `/identity/me` → `features.access{}` menü/widget filtresi. Uygulayan uçlar: ana sayfa widget'ları (→ bkz. 11.3.13), `documents/me`, `assets/me`, rehber `WorkPhone` maskesi, org şeması SS, özel alan DTO'ları, sol menü Takvim, izin takvimi kapsamı Department ↔ Company (yalnız "izinli" bilgisi, tür yok → bkz. 11.3.5).
- **DETAY — Davet akışı** [Ekranda]: kartta fotoğraf üstü / üç nokta → **Davetiye gönder** (onay diyaloğu); toplu **Toplu işlemler → İşlem seç → Giriş bilgilerini gönder**; hedef = iş e-postası, yoksa kişisel e-posta; e-posta yoksa 422 `identity.invitation.emailRequired`; çalışan bağlantıdan parolasını oluşturur. `Invitation` ek alanlar `SentToEmail, EmailSource(Work/Personal), SentByUserId, BatchId?`; toplu gönderim Hangfire job + sonuç özeti (gönderildi / e-posta yok / zaten aktif).
- **DETAY — Davet edilen çalışanın varsayılan durumu** [Ekranda]: `Employee` rolü; yalnız kendi kartı + erişim ayarlarıyla açılan alanlar; sol menüde **Talep** (izin, avans, harcama, FM, vize belgesi). Ad+Soyad ile kart açılır, hesap sonradan bağlanır; grid'e `HasUserAccount` / davet durumu kolonu ve filtresi.
- **FARKLI — ATS rolleri ve ilan bazlı erişim** [Ekranda]: ATS'de Admin / Admin − teklif şablonları (ad belirsiz) / **Limited Member** / **Interviewer**; kullanıcı bazlı "İş talebi oluşturabilir mi", "İlan oluşturabilir mi"; ilan formunda **Erişim** listesi (kişi yalnız o ilanın adaylarını görür). SenseİK: `Recruiter` = Admin; `Interviewer` Custom kapsam = atanmış mülakatlar ∪ `JobPostingAccess{JobPostingId, UserId}` (Recruitment, → bkz. 11.3.11); yeni sistem rolü `RecruitingMember` ("İşe Alım Üyesi") [Aday, öneri]; anahtarlar `UserPermissionOverride` ile (`recruitment.requisition.create`, `recruitment.posting.create`); `recruitment.offer_template.view`, `recruitment.sensitive.view` ayrı izinler. Ayrı ATS hesabı yok.
- **DETAY — Kullanıcı listesi (ATS örneği)** [Ekranda]: kolonlar ad, e-posta, **Durum** (Aktif/Pasif satır içi anahtar), Rol; "+" → e-posta + rol → Kaydet → hesap açılış e-postası; **Aktif olmayan kullanıcıları göster**; Google hesabıyla parolasız giriş (SenseİK'da SSO, Bölüm 4 #10). Pasif = `Status.Disabled`, yeniden aktif edilebilir.
- **DETAY — Hesabım tercihleri** [Ekranda, ATS]: Dil (TR/EN/**DE** [Aday]), Saat dilimi, Tema (Açık/Karanlık) → `ApplicationUser{PreferredLanguage, TimeZone, Theme}`; bildirim/takvim tercihleri → bkz. 11.3.13 / 11.3.11.
- **DETAY — Platform personeli kiracı verisine varsayılan erişemez** [Müşteri]: kurucu beyanı (part6). `ImpersonationGrant{TenantId, PlatformUserId, ApprovedByUserId, Reason, ExpiresAt}`; Owner onayı olmadan impersonate yok; audit + Owner'a bildirim (plan notu güçlendirildi).
- **DETAY — Ayarlar menüsü (kimlik kısmı)** [Ekranda]: Sistem ayarları → **Erişim ayarları**, **Ödeme bilgileri** (→ 3.20), **Vize** (→ bkz. 11.3.9); Şirket bilgileri → birim satırı → **Birim yetkilendirme**. Rotalar `/admin/settings/access`, `/admin/organization/units/:id/authorizations`, `/admin/billing`.
- **DETAY — Uygulama içi destek girişi** (Hesabım > Destek > Desteğe bağlan, sol alt **Destek**) yalnız referans → bkz. 11.3.13.

**İş kuralları ve hesaplama**
- Hesap sahibi ve Yönetici "tüm ayarlara, uygulamalara, veri aktarımına, genel ayarlara" erişir; tek fark **Ödeme bilgileri** sayfası: transkript "hesap sahipleri ulaşamıyor, sadece yöneticiler" (part8 #32) [Ekranda] ↔ plan 3.1: Owner = faturalama, Admin = Owner − faturalama. **Doğrulanmalı**; SenseİK plan yönünü korur (Billing 3.20 ekranları Owner), rol matrisi Admin'e `billing.*` verilmesine izin verir. "Hesap sahipleri" çoğul → birden fazla Owner; son Owner düşürülemez/silinemez (plan).
- Çalışan tipi yalnız kendi kartını görür; ek görünürlük "sizin izin verdiğiniz kadar" = Erişim ayarları (part8 #18, #32) [Ekranda]. Erişim ayarları Owner/Admin'i kısıtlamaz. **Özel alanlar** anahtarı birim yetkililerine uygulanır (part8 #10, #32); çalışanın kendi özel alanlarını görme/düzenlemesi alan tanımı düzeyinde ("beden" örneği, part1) → bkz. 11.3.3.
- **Birim yöneticisi** ayrı erişim türü değil, Çalışan tipindeki kişiye birim üzerinden verilen yetkidir (part8 #32) [Ekranda]: yalnız yetkili olduğu birim(ler)deki kartları listeler/açar, kişisel bilgileri ve kariyeri günceller, izin süreçlerini izler, kendi birimine yeni çalışan ekler; diğer kartlara ulaşamaz. Aynı kişi birden fazla birime yetkilendirilebilir (Satış-Pazarlama + İK örneği). Anahtar 1 kapalıysa ödeme/maaş bilgileri ve Finans raporundaki maaş kolonları görünmez; anahtar 2 açıksa kendi birimi için tüm hazır raporlar, **Kendin oluştur** hariç; 1 kapalı + 2 açık → maaş/ödeme içeren finansal raporlar hariç. "Genelde yöneticiler, şefler ya da müdürler için" (part8 #21) [Ekranda].
- Birim yöneticisi yeni çalışan eklerken şirket/şube alanları kendi kariyerinden ön-dolu gelir ve düzenlenebilir ("şubem Ankara, şirket Kolay İK"); birim yetkili olduğu birim(ler)le sınırlı; yönetici, çalışma şekli, kişisel bilgiler girilir (part8 #32) [Ekranda].
- Davet: kart Ad+Soyad ile açılır; e-posta girilmeden davet gönderilemez; her iki alanda e-posta varsa **iş e-postasına** gider; çalışan e-postadaki bağlantıdan parolasını oluşturup giriş yapar; sonrasında kendi kartındaki bilgileri görür/günceller, sol menüden izin/avans/harcama/FM/vize belgesi talebi açar (part8 #18, #19) [Ekranda].
- ATS: Admin her şeye erişir; ikinci rol Admin ile aynı, yalnız **teklif şablonlarını** göremez; Limited Member ve Interviewer için kullanıcı bazlı izin anahtarları; Interviewer yalnız **Erişim** verilen ilanların adaylarını görür, "diğer hiçbir alana erişemez"; **hassas veri** işaretli soru/form cevaplarını yalnız hassas veri yetkisi olanlar görür; pasife çekilen kullanıcı bağlanamaz, yeniden aktif edilebilir; kullanıcı eklenince hesap açılış e-postası; parola yok, Google hesabıyla giriş (part2 #1, #2) [Ekranda]. Yetki tablosu destek makalesinde.
- Platform: kurucu, müşteri verisini (performans, maaş) "güvenlik standartları gereği göremediğini" söylüyor (part6 #1) [Müşteri].
- Owner/Manager yetkisiyle puantajdan eklenen izin onaysız "Onaylanmış" (part1) → bkz. 11.3.4 (plan 3.4'te var).

**Akışlar**
1. Çalışan ekleme + davet (part8 #18): Çalışanlar → **Yeni çalışan ekle** → Ad, Soyad → Kaydet → kart açılır → E-posta → Kaydet → **Davetiye gönder** → davet e-postası → çalışan parolasını oluşturur → giriş → kendi kartı; sol menüde **Talep**.
2. Tekil davet (part8 #19): kart → üç nokta → **Davetiye gönder** → "Evet" → iş e-postasına (yoksa kişisel).
3. Toplu davet (part8 #19): Çalışanlar → **Toplu işlemler** → çalışanları seç → **İşlem seç → Giriş bilgilerini gönder** → seçilen her çalışana davet.
4. Erişim türü değiştirme (part8 #32): çalışan kartı → **Erişim türü** → Çalışan / Hesap sahibi / Yönetici → Kaydet.
5. Birim yetkilendirme (part8 #21, #32): Ayarlar → Şirket bilgileri → departman → üç nokta → **Birim yetkilendirme** → kişi seç → iki anahtar → Kaydet; ikinci birim için aynı adımlar; etki anında (kullanıcı sayfayı yeniler).
6. Erişim ayarları (part8 #10): Ayarlar → Sistem ayarları → **Erişim ayarları** → anahtarlar → **Kaydet**.
7. ATS kullanıcı ekleme (part2 #1): Ayarlar → Kullanıcılar → "+" → E-posta + Rol (+ alt anahtarlar) → Kaydet → bilgilendirme e-postası → Google ile giriş; **Durum** anahtarıyla pasif/aktif.

**SenseİK tasarım kararı**
- Entity / alan:
  - `UnitAuthorization{OrgUnitId, UserId, CanViewSalaryAndPayments, CanViewUnitReports, GrantedByUserId, IsActive}` — Identity modülü, `identity` şeması; unique `(TenantId, OrgUnitId, UserId)`; `OrgUnitId` yalnız Id (Organization entity'sine referans yok); doğrulama ve alt birim çözümü `IOrgUnitReadService{ExistsAsync, GetDescendantIdsAsync}` portu (Organization uygular); `OrgUnitDeleted` event'i ile ilgili yetkiler pasife alınır.
  - `Invitation` ek alanlar: `SentToEmail`, `EmailSource(Work/Personal)`, `SentByUserId`, `BatchId?`, `SentCount`.
  - `ApplicationUser` ek alanlar: `TimeZone`, `Theme(Light/Dark/System)`.
  - `ImpersonationGrant{TenantId, PlatformUserId, ApprovedByUserId, Reason, ExpiresAt, UsedAt?}`; `platform.tenant.impersonate` yalnız geçerli grant ile.
